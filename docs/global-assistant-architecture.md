# Global Medical Assistant lifecycle and emergency architecture

This report supplements the earlier [conversational redesign](conversational-redesign.md). Development used dummy process credentials and mocked provider responses. No real key was read, and no live Meta request was made.

## Investigation before this change

The earlier redesign had already replaced the primary conversation's disease catalog and retrieval gate with model planning, selective context, free generated blocks, and a provenance audit. Inspection of the current implementation found a different, remaining architectural restriction:

- Explicit danger, current warning signs, unresolved urgent alerts, and model-promoted urgency returned an emergency response before completing generation/audit/rendering. Recognition of danger cut off useful explanations instead of adding an independent safety layer.
- An unresolved urgent alert caused subsequent personal questions to take the same early-return branch, preventing normal follow-up reasoning.
- The API saved the turn only after synchronous reasoning. A slow/failing process could leave no durable question or immediately available warning, while the UI disabled submission throughout generation.
- Only review alerts carried conversations into ground snapshots. Ordinary educational turns were saved locally but omitted from the doctor workflow. A bounded recent-message window alone could also lose final updates to slow older turns.

These causes were identified from the execution path, rather than inferred from example wording. None requires a symptom-specific answer or a new disease catalog.

## Reusable implementation

1. **Save first.** The API commits the owned thread/turn, response, generation job, independent safety state, audit event, and encrypted downlink before remote generation. The React client requests immediate responses and polls the saved turn. Other API clients retain the optional synchronous mode for compatibility; explicit/inherited emergencies always return before remote work.
2. **Safety overlay.** `emergency_support.py` owns escalation, reference-based basic assistance, communication status, reported personnel availability, and installed approved procedures. The overlay stays visible above the model response. A model can escalate; it cannot remove an existing escalation. Follow-ups in an escalated parent chain retain the incident and reported unavailable personnel without disabling chat. Start a new conversation for a separate topic; an LLM does not provide clinical clearance.
3. **Continue reasoning.** `conversation.py` runs the same planner, selective record reader, free generator, and structural/provenance/policy validation for urgent and ordinary questions. Urgent context adds mission status, available support references, uncertainty, and instructions to explain possibilities and ask useful questions without delaying immediate action. Newly model-recognized urgency is published before one bounded enrichment pass with emergency context. No disease list, new symptom classifier, or per-question prose was added.
4. **One answer.** Generated short text uses IDs selecting the same explanation blocks shown in detail. Generated possibilities, questions, and next steps remain separate from local safety guidance. Emergency recommendations require supplied reference IDs; semantic support is checked by the automated audit. Differently worded useful explanations remain intact.
5. **Honest offline operation.** Model/network/validation failures retain local escalation and basic support references without fabricating clinical explanations. Approved procedures are loaded only from the installed protocol registry with `mission_approved` status. The seeded demonstration procedure is excluded. There are currently **no mission-approved clinical treatment procedures installed**. Public NIH/NASA information is not represented as mission approval.
6. **Recoverable work.** Additive `assistant_jobs` rows track queued/running/complete/failed/interrupted states. Atomic job claims prevent duplicate simultaneous generation. Restart marks unfinished work interrupted and preserves warnings; the owned retry endpoint can resume it explicitly. No provider exception bodies or authorization headers are stored in chat/audit output. Short write transactions reserve SQLite’s writer before read/modify work; synchronization savepoints have a real outer transaction, preventing partial commits and read-to-write lock conflicts with background jobs. Provider calls never hold this writer reservation.
7. **Doctor synchronization.** Every newly saved turn and response update queues the existing encrypted health-snapshot transport, including education without a clinical alert. Each update explicitly includes its changed turn even outside the recent-message window. Delivery upserts a separate ground conversation archive with capture/receive timestamps, protects against older snapshots overwriting newer answers, and retains older turns. Doctor APIs read delivered data only. Offline/link-delay policy applies equally to emergencies; local assistance never waits for it. The dashboard shows the most recent 100 delivered turns; the API supports pagination. Clinical review/return feedback/acknowledgment remain unchanged.

New API controls: `POST /api/assistant/messages` accepts `wait_for_completion:false` and optional `medical_personnel_available`. `GET /api/assistant/messages/{id}` polls the saved response. `POST /api/assistant/messages/{id}/retry` retries failed/interrupted jobs. `GET /api/doctors/conversations/{user_id}?offset=0&limit=100` reads the delivered archive. Astronaut status/retry operations enforce ownership; doctor archives require the existing doctor role.

## Deterministic rules that remain

The existing explicit warning flag, severity threshold, clinical warning-sign phrase/negation checks, unresolved urgent-alert checks, and conservative escalation actions remain independent of generated medical reasoning. They are finite prototype checks, not comprehensive triage. Explicit/inherited danger publishes immediately. Ambiguous text matches publish a conditional warning immediately while model scope distinguishes education from a current report; if planning fails, conservative local escalation remains. Intent interpretation can still fail, and a negative screen never means medical clearance.

Other deterministic behavior includes authentication/ownership, source allowlists/checksums, evidence-ID validation, metric schemas, bounded context, statistical monitoring thresholds, job states, delay/retry policy, operational failure text, and universal non-treatment escalation/support wording. Existing FTS token normalization/aliases and legacy trend/reference-only evidence selectors remain; they are not the conversational reasoning engine. Lexical retrieval can return irrelevant passages (for example, shared word stems); the model/audit must assess relevance rather than treat retrieval as proof.

## Verification

The backend regression suite covers unfamiliar presentations across cardiovascular, respiratory, neurological, musculoskeletal, renal/urinary, vision, minor-illness, and spaceflight categories. Each category exercises the same ordinary generation path and the same explicit-warning emergency path, including generated possibilities, recommendations, selected records, questions, and a continuing turn with changing information. Educational tests span endocrine, auditory, skin, pharmacology, cardiovascular, and spaceflight topics; empty local retrieval does not block generation or trigger clinical-profile reads.

Additional tests exercise model-promoted escalation and its enrichment pass, durable warnings during a blocked provider, provider failures, invalid citations, unsupported emergency actions, rejected audits, restart/retry, authentication/ownership, thread isolation, unavailable personnel, encrypted delayed/offline delivery, archiving beyond 20 recent turns, and late completion outside that window. Existing monitoring, ingestion, TLS/provider parsing/failure tests, and clinician feedback tests remain included.

Chrome workflows exercise astronaut-to-doctor feedback and acknowledgment, history/manual ingestion/export/simulator/mobile layout, bundled offline assets, honest generation-unavailable behavior, generated education/follow-up/selective personal context, and emergency warnings visible before a deliberately delayed mock model finishes. The emergency browser test submits another turn while generation is outstanding, opens its detailed generated explanation, and checks both delivered questions in the doctor archive. A seventh workflow runs four concurrent background generations alongside polling and six simultaneous synchronization requests, checking completed answers in the delivered archive without HTTP failures. A backend rollback test verifies that synchronization savepoints cannot commit outside their outer transaction. The isolated mock server blocks remote model transport.

Final results: **131 backend tests passed; 7 Chrome workflows passed; production TypeScript/Vite build passed.** The existing Starlette TestClient deprecation warning remains non-failing. Broad mocked cases demonstrate reusable orchestration and contracts; they do **not** demonstrate real Muse Wonder's diagnostic reasoning, clinical accuracy, or prompt-injection resistance. Test questions/response fixtures live only in tests, not in production routing or answer selection.

## Remaining limits

- Live Muse Wonder behavior, latency, and real medical answer quality require operator testing. The semantic audit uses the same provider family and is probabilistic; verified IDs prove source identity, not clinical truth. Uncited general knowledge stays visibly unverified.
- Emergency coverage is limited by existing deterministic checks and model recognition. Unfamiliar danger can be missed. The assistant does not authorize treatment, guarantee a diagnosis, or implement future-health prediction.
- No mission-approved clinical treatment checklist has been supplied. This implementation supports installing approved registry entries but cannot manufacture clinical approval or substitute general first-aid text for authorized spacecraft procedures.
- Jobs run in the FastAPI process. SQLite persistence plus interruption/retry prevents silent turn loss, but this is not a distributed worker system. Use a single application worker; multi-process recovery/leases and automatic retry after process death are not implemented.
- Prompt memory is bounded to eight selected ancestor turns, rather than unlimited full-history recall. Only supported sensor metrics/test types are available. Astronaut history shows recent turns; durable records remain in SQLite. Older legacy conversations outside previously queued snapshots are not automatically backfilled into the new ground archive.
- The Earth link is an encrypted local simulation with configured wall-clock delay, not actual spacecraft communications. Data remain synthetic and the system remains a hackathon prototype.
